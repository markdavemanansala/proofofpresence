## 1. P1 — Main attendee entry still requires navigating the workbench

**Route/source:** `/#event=<eventId>&view=participant`; `public/app.js:722` (`readRoute` supports three workbench views), `:1097`–`:1125` (event context, heading, shared tabs/sidebar), `:1459`–`:1464` (unlinked wallet next action), `:1620` (required name/email form), `:1625`–`:1627` (free route, story and personal-history panels).

**Evidence and friction:** The actual `alice-spot.png` shows the participant using the full workbench layout with an event selector, three tabs, wallet/sidebar panels, seven status facts, free-route content and personal history. Source confirms a new authenticated wallet is first offered “Link your registration” and a name/email form before the deposit action. A person arriving from a Committed Spot registration has already made a ticket choice; the interface presents several unrelated decisions again. The isolated direct deposit prototype solves the visual entry problem, but that screen is not a supported main route in this frozen source.

**Proposed next screen — event commitment:** Add a stable, shareable event-specific deposit entry to the main app, such as `/deposit/<eventId>`, using the same trusted event projection and draft/signing flow. Above the fold: event name, exact deposit/currency/network, one sentence separating payment from host approval, and one primary action. Show a short `Connect wallet → Link registration if required → Review deposit` sequence. If name/email linkage remains mandatory, explain its purpose and keep it within this sequence; do not silently bypass identity policy. Put alternative free admission and event materials behind concise links. Retain the prominent fast-test notice where applicable and exact recipient/value/wallet/policy review before signing.

**Dependency / acceptance:** This is principally routing and presentation. Confirm whether existing registration policy requires the local identity step; no Luma API or inferred identity is assumed. A fresh wallet can complete the required commitment journey without opening organizer/case tabs or selecting an event again. Unsupported event/network and closed deposit states remain explicit.

## 2. P1 — Deposit confirmation lacks the receipt handoff the attendee needs

**Route/source:** Same participant route; `public/app.js:1371`–`:1381` (receipt fact), `:1619` (facts disclosure), `:1884`–`:1897` (12-entry plain-text transaction log on the cases view), `:2091`–`:2093` (short-hash success toast), `:697`–`:708` (success toast hides after 6.5 seconds). The owner-only `public/contract-inbox.js:489` already implements full transaction IDs and an explicit copy control; the participant page does not reuse it.

**Evidence and friction:** `alice-spot.png` exposes a full receipt only inside “All status details”; `alice-cases.png` repeats it at the bottom of the long cases page. The participant has no deliberate “Copy transaction ID” or configured return-to-registration action. Source confirms successful signing ends in a transient short-hash toast. This is the exact point where the user's original workflow requires a reliable reference to submit externally.

**Proposed next screen — deposit receipt:** After submission, keep a durable event-scoped receipt card or screen. States should be `Wallet request unresolved`, `Submitted / awaiting canonical verification`, `Verified`, and `Failed`, with the corresponding permitted next action. A verified receipt shows full transaction ID, `Copy transaction ID` with selectable fallback, amount, network, event and a safe configured “Return to registration” link. Keep “Deposit verified — host admission pending” visible when appropriate. Reload should recover the same receipt rather than require finding it in a general log.

**Dependency / acceptance:** Use the confirmed result and existing authorized receipt projection; validate event, wallet and transaction scope on deep links. A Luma return link is navigation only: external approval and any manual transaction-ID submission remain outside the app. Do not call a wallet request or merely observed hash a verified deposit, and do not re-enable a second deposit while the original is unresolved. Copy success must be announced accessibly.

## 3. P1 — Organizer work remains an import-first document rather than a work queue

**Route/source:** `/#event=<eventId>&view=organizer`; `public/app.js:1629`–`:1648` (`renderOrganizer`), `:1127`–`:1134` (`enhanceTables` moves import before people and deposits before attendance), `:1650` (`renderDepositReview`); `public/batch-actions.js:136`, `:612` (separate batch toolbar and complete server review); `public/app.js:340`–`:373` (saved approvals and exact-selection contract-registration follow-up).

**Evidence and friction:** Actual `owner-manage.png` is 4088 pixels tall and starts with the CSV/provenance form even though contract deposits are automatically available. People and the deposit inbox repeat linked guests in two sections; trusted check-in appears above deposit/admission review; then attendance publication and recovery administration follow. Frozen source retains this effective order through `enhanceTables`. The batch dialog already explains the selected people, blocked reasons and separate financial consequence; the surrounding page makes the owner decide which of several overlapping sections is the next task.

**Proposed next screen — organizer verification queue:** Keep the existing top-level navigation. Within Manage event, start on a compact `Deposits to review` task view backed by the existing owner-only inbox, with current source/block freshness, search, status filters and selection. Open the existing wallet/receipt detail dialog on demand. Keep distinct secondary task choices for `Guest decisions` and `Door check-in`; place reviewed CSV import under `Import an export` and financial publishing under `Publish attendance`. These can be local task switches rather than more application-wide tabs. After saving approvals, retain the current exact-selection “Review contract registration” follow-up as the next task, without silently registering or approving in Luma.

**Dependency / acceptance:** Reuse current inbox, selection and review components. Preserve exact verified participant ID + wallet joins; unlinked payer wallets must remain unnamed until verified. Admission batch and trusted check-in batch remain separate. Every selected row stays visible in server review, blocked rows cannot be dropped silently, and uncertain saves keep their journal/status lock. The owner can reach the first relevant deposit review without passing the CSV form; staff sees only permitted check-in tasks. No change to financial eligibility is implied.

## 4. P2 — The participant's case is buried beneath event-wide treasury information

**Route/source:** `/#event=<eventId>&view=cases`; `public/app.js:1778`–`:1820` (`renderCases` puts money summary first), `:1744`–`:1776` (event totals), `:1822`–`:1870` (`renderCase` and its multiple action rows), `:1487`–`:1496` (participant next action links to the general cases view).

**Evidence and friction:** In actual `bob-cases.png`, Bob's matched case appears after five event-money cards, reserve details, normal payout actions and explanatory copy. The same event-total-first page is shown to Alice, whose own attendance is already confirmed. Bob must distinguish the event's total reserved share from his case's current held share, then interpret matching, settlement, appeal advancement and ruling delivery controls together. The existing copy correctly distinguishes these states; its order is the friction.

**Proposed next screen — your case status:** For the challenged wallet, lead this view with `Your attendance case`, current stage, the next authoritative deadline and one applicable action/reason. Follow with a short `Challenge → Match → Final result → Contract settlement → Payment` timeline. Keep exact resolver/arbitrator IDs, organizer snapshot and source context in a details disclosure. Evidence/appeal operations stay available within the case. Put whole-event payments and other cases below, labeled explicitly. For an owner, use a case queue with next actions rather than pretending every case belongs to the current wallet.

**Dependency / acceptance:** Presentation may derive stages only from current case/finality/settlement/payment fields. The controlled test-arbitrator notice must remain prominent; it is not a real jury decision. Unsupported/unavailable rulings remain blocked. Separate matching deadlines and explicit contract settlement are preserved, including ruling 0 economics. From the participant next-action link, the person's case should be the first substantive panel, with the exact event/network retained.

## 5. P2 — Waiting for a payment has no focused, personal progress view

**Route/source:** Participant and cases routes; `public/app.js:1436`–`:1441` (generic default next action), `:1413`–`:1432` (personal payout fact), `:1599`–`:1610` (kickback step), `:1275`–`:1296` (`participantPayments` canonical categories), `:1808`–`:1817` (payout wait calculation), `:1884`–`:1897` (action log).

**Evidence and friction:** In actual `alice-spot.png`, all attendance steps are complete but the leading instruction is “Await the next event update”; the payout step says only “Payment not yet recorded”. A useful omission-window date exists elsewhere, and event-wide normal-payout eligibility is explained on the cases tab. Personal direct attendance payments, claims, refunds and possible later top-ups are dispersed between seven-check details, a general money dashboard and action logs. No actual completed final payment was observed, so this is a progress/presentation gap rather than a claim of incorrect settlement or delivery.

**Proposed next screen — your payment activity:** Let `Track your kickback` open a personal payment view with `What is waiting`, `What was actually delivered` and a chronological activity list. Where known, state the current wait precisely: challenge window open, unmatched matching window open, ordinary payout review available, matched share protected, final result awaiting contract settlement, or failed transfer claim available. A window end must say that review becomes eligible, not promise automatic payment at that time. Keep direct attendance payments, refunds, credit withdrawal and claims separately labeled; claims may combine credit types. Show later top-ups as separate receipts rather than rewriting an earlier payment as “all complete”. Event treasury totals can remain under a secondary disclosure or organizer view.

**Dependency / acceptance:** Existing canonical payment categories support a first presentation pass. A richer per-wallet payment timeline requires the primary owner to confirm that authorized payment records expose sufficient stable receipt/log references and recipient attribution; do not infer it from contract balance or `Finalized`. Historical sent amounts, current owed credit, unused payer credit and held case shares remain independent. A payment completion state requires successful canonical delivery evidence, not a confirmed `release`/`resolve` action alone.

## Suggested build order and limits

Build the main direct commitment screen and durable receipt together, then the organizer verification queue. Follow with the focused case and personal payment views using the same existing dialogs and status vocabulary. Keep the three everyday application tabs; do not add another dashboard or merge approval/check-in/financial transactions to shorten the flow. Carry the established typography, spacing, focus, 44-pixel controls, wrapping wallet references and disclosure patterns into each screen; choose any teal theme convergence as one deliberate visual-system change rather than mixing prototype and main tokens piecemeal.

This report contains no new mobile acceptance, timing, wallet, financial or deployment proof. Review proposed mobile/200% text layouts and real authorized role states in the next implementation pass. Audit artifacts must not be treated as permission to resume D signing or change any live deployment.
